# 编译速度基准（计划第 6 节）

`tools/bench.sh <navic> [行数...]` 用 `bench/gen` 生成等价的 navi 和 Go 项目（每个单元一个结构体、一个枚举、几个用到循环/Vec/HashMap/match/闭包/格式化的函数），测：

- 冷编译：navic 每次都要编自己的 std；Go 用一个只装了 std 的私有缓存（日常情况），另给一行完全不带缓存的 Go
- 无改动重编译
- 改一个函数体后重编译
- 峰值内存（`/usr/bin/time -l` 的 maximum resident set size）

脚本不碰用户自己的 Go 缓存。

## 结果（Apple M 系列，macOS 15，Go 1.26）

第六轮（2026-11-14 下午晚些，后端按活跃区间线性扫描分配 x19–x27 之后；10 核）：

|---|---|---|---|---|
| 1 万 | navic | 0.41s / 358MB | 0.01s / 26MB | 0.42s / 352MB |
| 1 万 | go build（std 已缓存） | 0.37s / 130MB | 0.10s / 23MB | 0.35s / 135MB |
| 1 万 | go build（无缓存） | 2.22s / 294MB | | |
| 10 万 | navic | 3.11s / 2.33GB | 0.04s / 82MB | 3.03s / 2.30GB |
| 10 万 | go build（std 已缓存） | 2.58s / 880MB | 0.11s / 22MB | 2.56s / 949MB |
| 10 万 | go build（无缓存） | 2.71s / 942MB | | |

冷编译是 Go 的 1.1 倍（1 万行）和 1.2 倍（10 万行）。寄存器分配一项让 navic 自己快了约 25%：之前每个函数只把用得最多的 9 个标量局部放进寄存器、整个函数独占，MIR 的临时值（一次定义一次使用）全在栈上；现在生命期不重叠的局部共用寄存器。另试了把不跨调用的临时值放进 x1–x7，没有收益（9 个已经够用），没保留。

结论：

- 无改动重编译和 Go 持平（navic 的构建缓存）。
- 冷编译和改一个函数体后的重编译是 Go 的 3.5–6 倍（1 万行约 3.5–4.5 倍，10 万行约 6 倍）：navic 单线程，也没有函数粒度的增量缓存；Go 的编译器在包内并行：文件并发解析，函数的后端（SSA、寄存器分配、生成机器码）用 `-c=N` 个 worker 并发（只编一个包时 N 可到 GOMAXPROCS），类型检查是单线程的；改一个函数体也只重编那个包。
- 计划里 "M9 与 go build 持平" 的目标还没有达到。

## 按 crate 分开编译（`NAVI_SPLIT=1`，docs/crates.md），2026-11-24

Apple M4（10 核），`navi build -a`（不用整个程序的构建缓存），各取两次的范围。

- "冷"：crate 缓存为空。
- "热"：std 已经在 crate 缓存里。
- 时间格式是"墙钟 / CPU"。

| 程序 | 整个程序一起编 | 分开编译，冷 | 分开编译，热 |
|---|---|---|---|
| hello world | 0.56s / 1.6s，670MB | 1.07s / 4.1s，1000MB | 0.46s / 1.0s，540MB |
| 编译器自身 | 1.97–2.01s / 9.4–10.1s，2.25–2.58GB | 2.60–2.65s / 11.5s，2.30–2.52GB | 2.01–2.11s / 8.5–9.6s，2.09–2.28GB |

产物大小：hello 1.15MB（整个程序一起编 1.12MB），编译器 11.8MB（12.1MB）。

结论：

- 小程序热编译更快、内存更少：std 的 MIR 和后端都省掉了。
- 编译器这样的大程序，热编译和整个程序一起编基本持平。省下的 std 后端时间，被合并目标文件（约 0.2s，单线程）和链接抵消了。
- 冷编译要先把整个 std 编一遍，所以慢；每个编译器版本只发生一次。
- 剩下的大头是前端：每次都要解析和检查 std，hello 约 0.5s。这要靠第 4 步的 `.navih` 省掉。
