# 编译速度基准（计划第 6 节）

`tools/bench.sh <navic> [行数...]` 用 `bench/gen` 生成等价的 navi 和 Go 项目（每个单元一个结构体、一个枚举、几个用到循环/Vec/HashMap/match/闭包/格式化的函数），测：

- 冷编译：navic 每次都要编自己的 std；Go 用一个只装了 std 的私有缓存（日常情况），另给一行完全不带缓存的 Go
- 无改动重编译
- 改一个函数体后重编译
- 峰值内存（`/usr/bin/time -l` 的 maximum resident set size）

脚本不碰用户自己的 Go 缓存。

## 结果（Apple M 系列，macOS 15，Go 1.26）

第二轮（2026-11-13 晚，加了 MIR 内联、常量原位读取、std 函数体延迟类型检查、可达性根收窄、固有 `to_string` 等之后；这次机器负载略高，Go 的数字也比第一轮慢一些）：

| 行数 | 编译器 | 冷编译 | 无改动 | 改一个函数体 |
|---|---|---|---|---|
| 1 万 | navic | 1.91s / 320MB | 0.03s / 27MB | 1.93s / 321MB |
| 1 万 | go build（std 已缓存） | 0.55s / 131MB | 0.09s / 22MB | 0.42s / 131MB |
| 1 万 | go build（无缓存） | 2.73s / 300MB | | |
| 10 万 | navic | 19.6s / 1.86GB | 0.15s / 82MB | 21.4s / 1.84GB |
| 10 万 | go build（std 已缓存） | 3.31s / 927MB | 0.12s / 22MB | 3.03s / 935MB |
| 10 万 | go build（无缓存） | 3.18s / 935MB | | |

hello world：0.29s（第一轮 0.59s）。

第一轮（2026-11-13）：

| 行数 | 编译器 | 冷编译 | 无改动 | 改一个函数体 |
|---|---|---|---|---|
| 1 万 | navic | 2.61s / 360MB | 0.03s / 27MB | 2.60s / 362MB |
| 1 万 | go build（std 已缓存） | 0.38s / 135MB | 0.10s / 22MB | 0.36s / 136MB |
| 1 万 | go build（无缓存） | 2.32s / 301MB | | |
| 10 万 | navic | 24.2s / 1.8GB | 0.18s / 84MB | 24.1s / 1.8GB |
| 10 万 | go build（std 已缓存） | 2.70s / 927MB | 0.11s / 22MB | 2.68s / 933MB |
| 10 万 | go build（无缓存） | 2.97s / 943MB | | |

结论：

- 无改动重编译和 Go 持平（navic 的构建缓存）。
- 冷编译和改一个函数体后的重编译是 Go 的 3.5–6 倍（1 万行约 3.5–4.5 倍，10 万行约 6 倍）：navic 单线程，也没有函数粒度的增量缓存；Go 的编译器在包内并行（10 万行时用了 3–4 个核），改一个函数体也只重编那个包。
- 计划里 "M9 与 go build 持平" 的目标还没有达到。
