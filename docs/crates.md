# 按 crate 分开编译（设计）

## 目标

现在每次编译都是整个程序一起编：std、依赖和用户代码放在同一个类型环境里检查，一起建 MIR、一起做逃逸分析和内联，最后生成一个目标文件；构建缓存也只有"整个程序"这一份。改一行用户代码，std 和所有依赖也要从头再做一遍。

目标是照 Go 的包缓存：**每个 crate 单独编译一次，结果（目标代码加导出数据）按内容存进全局缓存，所有项目、每次重编共用**。std 是第一个用上它的 crate，第三方依赖走同一条路径，不给 std 开特例。

预期收益（实现前后都用同一组场景量）：

- 小程序：现在一个十几行的程序也要从 std 拉进约 2100 个函数、4.7 万条 MIR 语句；std 有缓存之后只编用户代码和用到的泛型实例。
- 改一个函数后重编：只重编这个函数所在的 crate。
- 峰值内存：std 和依赖的 MIR 不再常驻。编译器自举时 std 的非泛型函数约占 MIR 的 17%，收益主要在小程序和依赖多的项目上。

## crate 的身份与缓存键

- **身份**：名字，加上版本（git 依赖用 tag，没有 tag 用提交号；路径依赖和项目自身没有版本），再加上内容哈希（源文件哈希）。`navi.toml` 不加版本字段，版本以 tag 为准（同 Go）。
- **缓存键**：编译器版本（编译器二进制的哈希）、目标平台、编译选项（cfg、features）、crate 所有源文件的哈希，以及它直接依赖的每个 crate 的**导出数据哈希**。依赖只改了内部实现、导出数据不变时，下游不用重编（同 Go）。
- 同一个程序里可以有同一个 crate 的两个版本：它们是两个不同的 crate（类型互不相同，符号互不冲突）。

## 每个 crate 编出什么

缓存里每个 crate 一项，包括：

1. **目标文件**：这个 crate 的非泛型函数、静态变量、只用到本 crate 类型的泛型实例、类型描述符和 vtable。
2. **导出数据 `.navih`**：下游编译时只读它，不再解析和检查这个 crate 的源码。内容：
   - 头部：格式版本、编译器版本、目标平台、编译选项、crate 身份、依赖的身份和导出哈希、本文件的哈希。
   - 模块树、`pub use`、prelude；对下游可见的条目（路径、种类、可见性和下游需要的属性：`track_caller`、`inline`、`deprecated`、`must_use`、`repr`、`link`、`export_name`）。
   - 类型定义：结构体和枚举的字段、变体、判别值、`repr`，以及布局需要的全部信息；类型别名；泛型参数和约束；常量的值；静态变量的符号。
   - trait 定义，以及**所有** impl 的头部和方法的符号（下游的方法解析和孤儿规则要用）。
   - 非泛型函数：签名、符号、调用约定，以及**逃逸摘要**（哪些参数逃逸、哪些流向返回值）。
   - 函数体（MIR）：泛型函数的（下游实例化要用），以及可内联的小函数的（下游跨 crate 内联要用），连同其中的闭包。
   - 语言项（只有 std 有）：运行时入口（`gc_alloc`、`panic_raw`、`morestack`……）和语言 trait。
   - 源文件表：MIR 里的位置能还原成"文件:行"（panic 消息、调试信息）。
   - 格式：二进制，一张字符串表加索引，下游按需读用到的条目。

## 符号命名

现在的符号是全局顺序编号（`_navi_123_name`、`_navi_ty45`、`_navi_vt6`），同一个函数在不同程序里编号不同，所以要先换成**稳定的命名**：由 crate 身份（名字、版本、内容哈希的前几位）、条目路径和（泛型实例的）类型参数或 shape 组成，过长的部分用哈希代替。同一个东西在任何一次编译里得到的名字都相同，不同的东西名字一定不同。

## 泛型实例

- 只依赖本 crate 和其依赖里的类型的实例（如 std 里 `Vec<u8>`），编在本 crate 的目标文件里。
- 依赖使用方类型的实例（如用户的 `Vec<MyType>`），编在使用方 crate 里（同 Go）。
- 不同 crate 可能各自生成同一个实例（都用了 `Vec<i32>`）：这类符号标成"可合并"，链接时同名的只留一份。类型描述符、vtable 同样处理。

## 跨 crate 优化

- **内联**（同 Rust）：非泛型函数只有标了 `#[inline]` 的，导出数据才保留函数体；下游调用到它时用函数体建一份 MIR 模板，只用来内联，不生成代码（没内联的调用仍是调用上游的符号，模板的逃逸摘要也不导出）。泛型函数本来就带函数体。std 照 Rust std 给基础模块（整数、`char`、`str`、`String`、`slice`、原子操作、`time`）里的小函数标了 `#[inline]`，std 的导出数据因此大了约 8%；用户代码里的 FNV 哈希循环快了 1.7 倍，hello world 的编译时间不变。
- **逃逸分析**：调用其它 crate 的函数时，用导出数据里的逃逸摘要；没有摘要的按"参数都逃逸"处理（保守，只影响性能）。
- 生成的代码与整个程序一起编时可能略有差异（个别分配从栈上变到堆上）；用基准量这一点。

## 链接

自研链接器（Mach-O、ELF、PE）改成接收多个目标文件：合并各个段，按名字解析跨文件的引用，"可合并"的同名符号只留一份。用系统链接器的路径（`--linker cc`）本来就支持多个目标文件。

实际做法（`compiler/src/merge.navi`）：链接前先把各个目标文件合成一个，再交给原来的链接器。合并时删掉程序用不到的部分：

- 每个段按符号切成块：一个函数（连同它内部的标号）、一个字符串、一个静态变量、一张表。
- 从入口出发，沿重定位标记能到达的块，没到达的不复制。单独编出来的 crate 带着程序可能调用的全部函数，不删的话 hello world 有 7 MB，删完是 1.15 MB，整个程序一起编是 1.12 MB。
- 栈图表按留下的函数重建。
- crate 的初始化函数给每个静态变量单独调用一个初始化函数。只有静态变量本身被用到，这个调用才保留；否则改为调用空函数 `_navi_init_nop`。这和整个程序一起编时只初始化用到的静态变量一致，启动时也不会跑 std 里全部静态变量的初始化。
- `-d nostrip` 保留全部块。

## 现状

程序依赖的每个 crate（std、path 依赖、git 依赖）都单独编译（2026-11-24 起总是这样，开关 `NAVI_SPLIT` 和整个程序一起编的方式去掉了）：

- 编译顺序是依赖在前。编一个 crate 时，它依赖的 crate 里的非泛型函数都按外部函数处理。
- 程序的 main 按同样的顺序调用各个 crate 的初始化函数。

每个 crate 在构建缓存里有两个文件：

- `<key>.lib`：目标文件和逃逸摘要（`compiler/src/libcache.navi`）。
- `<key>.navih`：导出数据（`compiler/src/navih.navi`）。

缓存键在读 crate 之前就能算出，由以下几项组成：

- 编译器身份
- 目标平台
- 影响代码生成的 `NAVI_*` 开关
- crate 名
- crate 目录下每个 `.navi` 文件的相对路径和内容哈希（std 的 132 个文件约 4ms）
- 它的依赖的缓存键

关于键的几点说明：

- 键里放的是依赖的键，所以改动 bar 会让 bar 和依赖 bar 的 foo 重编，std 照样命中缓存；只改 foo 则只重编 foo。
- git 依赖的版本（tag 或锁定的提交）体现在检出的源文件内容里，不用单独进键。
- crate 一律带调试信息编译；构建不要调试信息（`-s`）时，合并前去掉它的行表。所以键里没有这一项。

**导出数据（第 4 步第一版）**：存的是 crate 各个文件的语法树，编解码器由派生宏 `#[derive(Codec)]`（`compiler/codec`，docs/derive.md）从 `ast.navi` 的各个类型生成（原来是 `tools/gen_astcodec.py` 生成的 `syntax/astcodec.navi`，编码不变）。

- **去掉的函数体**：下游不会编译的函数体，换成空块并标上 `elided`。
- **保留的函数体**：
  - 泛型函数，包括 impl 或 trait 带类型参数、参数里有 `impl Trait` 的；
  - const fn；
  - 返回 `impl Trait` 的函数（隐藏类型要从函数体得到）；
  - 函数体里声明了条目的函数。
- **读取方式**：前端遇到 `.lib` 和 `.navih` 都在缓存里的 crate，就用这些树代替读文件和解析。名字解析和收集签名照常进行。
- **当作已检查**：这样读进来的 crate 和 std 一样，函数体按需检查，ADT、impl、trait 和 impl 重叠也不再检查。这些在它单独编译时已经检查过。
- **出错保护**：万一要检查一个被去掉的函数体，报内部错误，不会悄悄出错。
- **文件名**：不存进导出数据，按 crate 现在的目录重新拼出来（符号名靠它得到相对路径，crate 换了位置也一样）。
- **大小**：std 的导出数据 1.4MB；全部函数体都保留时是 2.7MB。`navi navih-check` 检查编解码前后的树逐个相同。

**解码**：每个文件单独编码，块头记下它有多少带 id 的节点，所以各个文件可以分给多个线程解码。线程数和解析一样取 `available_parallelism()`，也就是 `NAVI_MAXPROCS`。节点 id 按文件预留区间，和线程数无关。

hello world 热编译时：
- std 的解析从约 51ms（多线程，CPU 约 250ms）变成解码约 5ms（单线程 26ms）；
- 整个"解析和名字解析"阶段从约 90ms 降到 43ms。

**LSP**（`navi lsp`）也从导出数据读依赖。它不编译，所以只要求 `.navih` 在缓存里；从源码读的依赖分析完顺手存一份。

- 读进来的文件没有源码文本，悬停取文档、跳转、建索引要用的文本，按路径从磁盘读回（内容和导出数据一致，键就是按内容算的）。
- 算键时编辑器里未保存的文本也算在内，和解析时一样。
- 补全、悬停（含文档）、跳到 std 里的定义，结果和从源码读时相同。

下一步：

- 收集签名的结果也存进去（第二版）。实测热编译时收集 std 的签名约 30ms（11,531 个定义），从文件解码同样的信息也要十几 ms，能省的约 15–20ms，却要序列化整套类型系统；暂不做。
- 几份 LSP 分析共享同一份依赖数据。

## 自举

- 编译器和 std 的源码只能用 v0.0.3 支持的特性。这一项只改编译器的实现，不需要新的语言特性。
- 导出数据和缓存只是编译器的内部格式：格式版本或编译器版本一变，缓存全部失效，不需要兼容旧格式。
- stage2 和 stage3 仍要逐字节相同；用不用缓存，产物的行为必须一致（但符号和布局可以不同）。

## 分步计划（每一步都能单独验证和提交）

1. **稳定的符号名**：编号换成按身份和路径的命名。产物行为不变；自举定点和"任意线程数逐字节相同"照常检查。
2. **链接器接收多个目标文件**，支持"可合并"的符号：先用"把现在的一个目标文件拆成两个"来测。
3. **按 crate 生成目标文件**：前端仍然整个程序一起做，后端按 crate 把代码分到各自的目标文件里。泛型实例按上面的规则归属，最后合在一起链接。测试全过、行为不变。
4. **导出数据的写和读**：一个 crate 编完写出 `.navih`；下游编译时读 `.navih` 代替解析这个 crate 的源码（类型、trait、impl、签名、泛型和小函数的 MIR、逃逸摘要）。这一步最大，先拿 std 做。
5. **按 crate 缓存**：缓存键如上，缓存里存目标文件和 `.navih`；`navi build` / `navi test` 对每个依赖先查缓存、缺了才编。
6. **依赖 crate** 走同一条路径；`navi.lock` 锁定的提交进入缓存键。
7. **量收益**：hello world、编译器自举、10 万行生成项目，测冷编译、改一行后重编、峰值内存，记入 `docs/bench.md`。

## 风险

- 第 4 步的工作量最大：导出数据要覆盖前端用到的全部信息，任何遗漏都会让下游的类型检查和"整个程序一起编"不一致。可以先用"整个程序一起编"和"读导出数据"两种方式编同一组测试，对比各自得到的类型和签名来查遗漏。
- 跨 crate 内联和逃逸分析变保守，可能让 std 密集的代码变慢；用基准量，必要时扩大导出 MIR 的范围。
- `-d checkstd`（检查 std 所有函数体）在 std 单独编译时自然就是全量检查；惰性检查 std 函数体这一优化会随之改变。
