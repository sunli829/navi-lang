# SSA 后端设计

navic 现在的后端（`compiler/src/backend/lower.navi`）把 MIR 逐条语句翻译成机器码：
- 标量局部变量按整个生存区间提升到被调用者保存的寄存器（arm64 x19–x27，x64 两个）；
- 其余值放在栈帧里，中间结果经过固定的中转寄存器（x12/x13 等）。

这种做法编译快、可靠，但有两个结构性的上限：

1. **优化都要绕路做**。MIR 的局部变量会被反复赋值，长度、指针要从内存读：
   - copyprop 要自己证明"只赋值一次、没被借用"；
   - 边界检查消除要先证明"两次读到的是同一个值"。

   在 SSA 上，这些都是值的身份问题。
2. **寄存器用得差**：
   - 调用者保存的寄存器（arm64 x1–x7、x10–x15、f2–f31）几乎不用；
   - 值在寄存器之间来回搬；
   - 每个提升的局部变量独占一个寄存器，跨越整个生存区间。

这份文档是用 Go 的 SSA 后端（`cmd/compile/internal/ssa`）的做法取代 lower.navi 的方案。

## 1. 原则

- **参考 Go，按我们的规模裁剪**：
  - 数据结构、pass 的顺序和寄存器分配算法都照 Go；
  - 不做规则生成器（`_gen/*.rules`），lowering 和化简手写；
  - 不做 Go 那些边际收益小的 pass。
- **调用约定和 runtime 约定不变**（第 2 节）：
  - 新旧后端生成的函数可以互相调用；
  - runtime（栈扫描、栈移动、调度器的上下文切换）不用动。
- **逐函数回退**：SSA 后端遇到还不支持的 MIR 就交给旧后端，覆盖面逐步扩大。每个阶段都能完整自举、全量验证。全部覆盖后默认开启，再删掉旧后端。
- **编译速度有预算**：自举现在约 1.9 秒，开启 SSA 后最多慢 15%。做法同 Go：
  - 值和块用稠密编号，存在 Vec 里；
  - 用 sparse set，不用 HashMap；
  - 每个函数一个 arena，复用在 `g.live` 那样的线程缓存里。

## 2. 保持不变的约定

| 项 | 约定 |
|---|---|
| 参数 | 栈上传递，被调用者在 FP+16 起读取 |
| 结果 | RET 寄存器给出结果槽地址 |
| 特殊寄存器 | CTX（字典或闭包环境）、LOC（`#[track_caller]` 的位置）、GREG（当前 G） |
| 帧 | 固定槽 SLOT_CTX/RET/LOC/DEFERS；序言里做栈检查，不够时走 morestack 存根 |
| 被调用者保存寄存器 | arm64 x19–x27、x64 rbx/r12：谁用谁在序言里保存。栈图给出每个调用点哪些保存寄存器装着指针（栈移动时据此修正） |
| 帧的指针位图 | 整个函数一张。标为指针的槽在序言里清零（和现在一样） |
| 安全点 | 只有调用（抢占是在序言处协作式的） |

Go 没有被调用者保存寄存器：跨调用的值一律溢出到栈上。我们保留被调用者保存寄存器，并把它们用在跨调用的值上，这比 Go 少一些溢出。改成 Go 的寄存器 ABI（参数和结果走寄存器，Go 1.17 带来约 5% 的提升）留到最后单独做（阶段 S7）。

## 3. IR

新模块 `compiler/src/ssa/`。

- **`Func`**：
  - blocks、values（按编号）、入口块；
  - 局部变量的帧槽；
  - 每个调用点的位置标签（栈图用）。
- **`Block`**：
  - kind：Plain、If（控制值是 bool 或 flags）、Ret、Exit（panic 之后的 trap）；
  - succs/preds，以及最多一个控制值；
  - values 按调度顺序排列。
- **`Value`**：
  - 字段：编号、op、类型、args、aux_int、aux（符号、MIR 常量、调用信息）；
  - 所在块、use 计数。
- **类型**：
  - 位宽：I8/I16/I32/I64、F32/F64、Bool；
  - Ptr：GC 指针，栈图要知道；
  - UPtr：runtime 里当整数用的地址；
  - Mem、Flags、Tuple（多结果，用 Select0/Select1 取）。
- **内存状态是 SSA 值**（同 Go）：
  - 入口有一个 InitMem；
  - Load 读一个 mem 参数；
  - Store、Zero、Move、调用读一个 mem 并产生新的 mem。

  这样 CSE 和 prove 只要比较值的身份和 mem 参数，就知道两次读取是否等价。
- **op 分两层**：
  - 通用 op：Add、Sub、Mul、Div、Rem、And、Or、Xor、Shl、Shr、比较、Neg、Not、Zext、Sext、Trunc、浮点转换、Const、Addr（帧槽地址）、OffPtr、Load、Store、Move、Zero、Phi、Copy、Call、IsInBounds、Select 等；
  - 每个架构自己的 op：带寻址方式的 load/store、带立即数和移位的算术、Cmp + 条件分支等。

  lowering 把前者换成后者。

## 4. 从 MIR 构造

时机：MIR 流水线不变（逃逸分析 → 装箱 → simplify → 内联 → copyprop），后端按 GC shape 实例化每个函数时构造 SSA。

**哪些局部变量变成 SSA 变量**：
- 条件和现在的寄存器提升一样（liveness 里的 `bad`）：标量、指针、函数指针，只整体读写，或者只用来解引用；
- 胖指针（切片、`&str`、`&dyn`）拆成两个变量：指针，和长度或 vtable（同 Go 的 decompose）。

**其余局部变量**：结构体、枚举、数组、被取了地址的变量，留在帧槽里，读写变成 Addr + Load/Store。

**phi 的插入**：用 Braun 等人的算法（2013，"Simple and Efficient Construction of SSA Form"）。
- 它直接在我们的 CFG 上边走边建，不需要先算支配边界；
- 平凡的 phi 当场删掉，结果是最少的 phi。

Go 的 `phi.go` 对小函数用的是类似的思路。

**各类 MIR 的翻译**：
- 语句和 Rvalue：一一对应成通用 op；
- 投影（字段、解引用、下标）：展开成 OffPtr 和地址计算；
- `Len`：读胖指针的第二个变量，或者常量；
- 下标检查：MIR 的 `Assert{bounds}` 变成 IsInBounds 加一个分支，分支的另一头是 panic 块。

**调用**：Call 值，参数在调用前用 Store 写到出参区（SP+off），结果在调用后从结果槽 Load 回来。保持现有约定。

**内建函数**：
- 能翻译成 op 的翻译：wrapping 运算、atomic、`ptr_offset`、`slice_from_raw` 等；
- 其余（`swap_context`、`spill_registers`、`resume_context` 等 runtime 专用的）先让整个函数回退到旧后端，最后再逐个支持。

## 5. Pass（顺序照 Go 的 `compile.go`，括号里是对应的 Go pass）

| 阶段 | pass | 说明 |
|---|---|---|
| 通用 | copyelim、phielim | 去掉 Copy 和只有一个不同输入的 phi |
| | deadcode | 从控制值、有副作用的值往回标活 |
| | opt | 手写的常量折叠和代数化简（x+0、x*2^k→shl、比较常量） |
| | cse | 同 Go：先按 (op, type, aux, 参数个数) 分区，再按参数的分区反复细分 |
| | prove | 边界检查消除，见下 |
| | deadcode | |
| 降低 | lower | 通用 op → 架构 op（手写，每个架构一个 match），顺带做寻址方式 |
| | lowered cse、deadcode | |
| | critical | 拆开关键边，regalloc 只在单后继块的末尾放调整代码 |
| | layout | 块的排列：沿用 MIR 的顺序，优先让后继紧跟着（落空） |
| | schedule | 块内排序：保持 MIR 的顺序，把产生 flags 的比较挪到用它的分支前 |
| | regalloc | 见第 6 节 |
| | stackalloc | 溢出槽分配，见第 6 节 |
| 生成 | genssa | 按架构生成机器码，见第 7 节 |

**prove**（Go 的 `prove.go` 加 `loopbce.go`）：
- 从入口沿支配树往下走，进入一个 If 的后继时，把条件作为事实加进事实表，离开子树时撤销；
- 事实表记录值之间的 <、≤、=，以及每个值的上下界；
- IsInBounds(i, len) 能推出成立就删掉检查，推出不成立就删掉那个分支；
- 归纳变量：识别 phi(初值, phi+步长) 加上用循环条件守着的循环，给出 初值 ≤ i < 上界；
- `for i in 0..n` 内联后，Range 结构体的字段是 SSA 变量（结构体不被取地址时同样拆开，见下），可以照此处理。

**结构体拆分**（Go 的 decompose）：只有标量字段、从不被取地址的小结构体局部变量（如内联后的 Range、Option<usize>），按字段拆成 SSA 变量。S5 再做。

## 6. 寄存器分配和溢出槽

照 Go 的 `regalloc.go`：
- 把整个函数当成一条按 layout 顺序排列的长基本块，贪心分配；
- 用到某个值时才把它装进寄存器；寄存器不够时，赶走下次使用最远的值；
- 每个块的初始寄存器状态取已分配的那个前驱的出口状态；其他前驱在边上补移动（关键边已经拆开）；
- 溢出的放置：在所有恢复点的公共支配者里，找一个值还在寄存器中的位置放 StoreReg；
- phi 分两种：寄存器 phi（输入和 phi 用同一个寄存器）和栈 phi。

**我们的不同之处**：
- **跨调用的值**：
  - 先算出每个值的活跃区间是否跨过调用；
  - 跨调用的值优先放被调用者保存寄存器（用到的才在序言里保存，和现在一样），放不下再溢出；
  - 不跨调用的值放调用者保存寄存器；
  - 调用时，调用者保存寄存器里的活值（只可能是来不及处理的）一律溢出。
- **栈图掩码**：每个调用点上，被调用者保存寄存器里有哪些装着 Ptr 类型的活值，直接从分配状态读出来，填进现有的掩码表。
- **溢出槽（stackalloc）**：
  - 指针值和非指针值分两个区；
  - 区内按干扰关系复用；
  - 指针区记进帧的指针位图，在序言里清零（第 2 节）。

**可分配的寄存器**：
- arm64：
  - 整数：x1–x7、x10–x15 由调用者保存，x19–x27 由被调用者保存；
  - 浮点：f2–f31（其中 v8–v15 的低 64 位按 AAPCS 由被调用者保存，C 调用时注意）；
  - 保留：x0（CTX）、x8（RET）、x9（LOC），以及 x16/x17、x18、x28（G）、x29、x30。
- x64：先按 Go 的 amd64 寄存器表定，扣掉我们的特殊寄存器和 rbx/r12；除法、移位等固定寄存器的 op 由每个 op 的寄存器约束（Go 的 regInfo：输入、输出、clobber）表达。

## 7. 代码生成

- 每个架构一个 `gen_value` / `gen_block`：
  - 直接用 `arm64.navi` / `amd64.navi` 里的汇编器（Asm）发射指令；
  - 寄存器是 regalloc 给的物理寄存器。
- 序言（栈检查、保存寄存器、清零指针区）、C 调用（`call_c`，切换到系统栈）、morestack 存根、defer 和 panic 的调用序列，都是现有 Machine 里的代码。把它们的寄存器参数改成物理寄存器编号后复用，不重写。
- 分支：
  - 后继紧跟着就落空；
  - If 的控制值是 flags 时直接发条件跳转，不再先 cset 再 cbnz。
- 行号表、调用位置标签、`#[track_caller]` 的 LOC：值上带 MIR 的位置，生成时和现在一样记录。

## 9. 风险

- **GC 正确性**：
  - 跨调用的指针值必须在被调用者保存寄存器（带掩码）或指针区的溢出槽里，regalloc 的不变式要由校验器检查；
  - 派生指针（数组元素地址、字段地址）是内部指针，GC 已经支持；
  - runtime 和 std 的保守扫描标志照旧。
- **栈移动**：指向栈的地址可能出现在溢出槽和保存寄存器里，二者都在位图或掩码中，栈移动时会被修正，和现在一样。
- **确定性**：所有遍历按编号顺序，不遍历 HashMap，保证自举 FIXPOINT 和多线程构建的结果一致。
- **工作量**：预计新增 7000–9000 行 navi，跨多个会话完成。S1–S3 是主体，旧后端在 S6 之前一直可用，任何时候都能回退。

## 10. 进度

- **S1（完成）**：`compiler/src/ssa/`（IR、`dom.navi` 支配树、`check.navi` 校验器、copyelim、deadcode、打印）和 `compiler/src/backend/ssagen.navi`（从 MIR 构造）。
  - 开关：
    - `-d ssacheck`：构造并校验每个函数，最后报告建成和没建成的个数；

    - `=3`：只构造，不校验；
    - `-d ssadump=名字`：打印名字里含这个字符串的函数的 SSA。
  - 结果：自举的 4895 个函数、tests/run 的全部程序都能构造，并通过校验。
  - 耗时：单线程下，构造让后端阶段从 808 ms 涨到 1257 ms，校验再加约 80 ms。其中 `site_target`、place 类型查询这些开销旧后端也有，S2 换掉旧后端后不会叠加。哈希表和清理 pass 的开销留到 S2 接上完整流水线后统一优化。
- **S2–S4（完成，默认关闭，`NAVI_SSA=1` 开启）**：寄存器分配（`ssa/regalloc.navi`）、分配前的准备 pass（`ssa/prep.navi`）、代码生成（lower.navi 末尾的 SSA 部分），arm64 和 x64 上全部函数都能生成。
  - 寄存器分配：线性扫描，每个值一个区间。跨调用的值只能放进被调用者保存寄存器，arm64 另外分配 x1–x7。放不下时溢出结束最晚的区间；溢出槽分指针和非指针两类，按区间复用。
  - 常量、帧地址、vtable 不占寄存器，用到时现场生成。
  - 只在分支里用到的比较和分支融合成 cmp + b.cond；偏移折进 load/store；关键边拆开后，在前驱末尾插入并行移动来实现 phi。
  - 栈图：每个调用标签对应一个寄存器掩码，指针溢出槽加进帧位图。
  - 内建函数、闭包、defer、C 调用经"桥接区"复用旧后端的 helper：SSA 参数先存进帧里的缓冲区，旧 helper 通过假局部变量读取。旧 helper 拆成主体和尾部，旧路径生成的代码不变。
  - 浮点仍按位放在整数寄存器里。x64 只分配 rbx、r12，其余溢出到栈上。

    - SSA 编出的编译器能自举到 FIXPOINT（arm64；x64 在 Rosetta 下也一样），NAVI_MAXPROCS 1 和 16 的结果相同；
    - tests/run 在 arm64 的 5 种压力模式、x64 的 2 种模式、Android 的 2 种模式下全部通过；
    - 5 个目标上的 `-d checkstd` 和交叉编译通过。

    |---|---|---|
    | regex 查找/捕获 | 230/316 ms | 159/220 ms |

- **S5（第一部分）**：`ssa/opt.navi`，`-d nossaopt` 关闭。
  - CSE：沿支配树做带作用域的值编号；Load 带着内存参数参与编号，所以中间没有写的两次读取会合并。
  - 简化版 prove：在支配树上传递分支条件的真假，已知条件的分支改成直接跳转，再删掉不可达的块。`while i < v.len() { v[i] }` 这类循环里的边界检查就这样被消掉了。

  - 效果：在模拟器负载下测，压缩约快 5–8%，regex 基本持平。
- **S6（第一部分，完成）**：SSA 后端设为默认，`NAVI_NOSSA=1` 退回旧后端。全量验证（`/tmp/sl_fullval.sh`）全部通过：stage0 自举、selfcheck、go test、确定性、5 个目标的 std 检查和交叉编译、arm64 的 5 种压力模式、x64（Rosetta）的 4 种模式、Android 的 2 种模式。旧后端的代码暂时保留，等 SSA 后端稳定一段时间后再删。

  - 调用目标在构造时解析一次，存进 `Aux::Call`；
  - 块末定义和支配树孩子改用扁平数组；
  - `Vec::resize` 先 reserve；
  - 切片迭代器的 `next` 内联。

  结果：10 万行冷编译和旧后端相比从 +25% 降到 +5%（交替测量的平均值），改一个函数体后的重编译相同。剩下的开销分散在构造（约 480 ms）、寄存器分配（约 250 ms）、生成（约 390 ms）和优化（约 120 ms）里（单线程，10 万行工程）。
- **S5（第二部分）**：
  - **块布局**：跳过只有跳转的空块，带 panic 的冷块排到最后。
  - **LICM**（`opt::licm`）：自然循环的前置块收纳循环不变的值。头块里的纯运算都可以外提，Load 只要内存来自循环外也可以；其他块里只外提不会 panic、不读内存的运算；比较不外提，以免拆散和分支的融合。
  - **浮点放进浮点寄存器**：新增 Machine::fload/fstore/fmov。arm64 用 v2–v7、v16–v31，x64 用 xmm2–xmm5，都由调用者保存，跨调用的浮点值溢出。
  - **CTX、RET、LOC 参与分配**：这三个寄存器只在调用前一刻才设置，作为调用者保存寄存器分配，x64 也因此有了可用的寄存器。
  - **内建调用改写**（`mir/builtin.navi`）：基本类型上的比较和 clone 调用改写成运算。
  - **第二轮内联**：只处理第一轮里内联过代码的函数。
  - **`#[inline(always)]`**：不受大小限制，用在 `Range::next` 上；整数的 `StepChecked` 改成不调用函数的写法。
  - 结果：Mandelbrot 251 → 54 ms，点积 170 → 113 ms，`for i in 0..n` 求和循环 1.5 s → 0.29 s，自举耗时持平。
- **聚合局部变量拆分**：
  - 引用转发（`mir/refprop.navi`）：`p = &r` 只赋值一次、`p` 只被解引用时，`(*p).x` 改写成 `r.x`，删掉这条借用。内联进来的方法的 `&mut self` 就是这种情况。
  - 构造器把只通过字段访问的结构体、元组和枚举局部变量拆成变量：枚举是一个变体编号，加上每个变体的字段。允许的用法包括字段读写、Discr、SetDiscr、整体 Aggregate 或零值赋值，以及同类型的拆分局部变量之间的整体拷贝。
  - `for i in 0..n` 里 `next` 返回的 Option 因此不再经过内存，求和循环从 0.29 s 降到 0.20 s，和手写的 while 循环一样。
- **S6（完成）**：删除旧后端。旧的逐语句翻译、按局部变量的寄存器分配、旧的调用生成、活跃性结构和 `NAVI_NOSSA` 都已删除；内建函数、闭包、defer、C 调用仍通过桥接区使用原来的 helper。`-d ssacheck`/`-d ssadump` 在 `try_ssa` 里校验和打印刚构造出的 SSA。
- **跳转线程化与来自调用结果的拆分**：
  - `mir/thread.navi`：对前驱刚构造好的枚举变体做分支时，把分支块复制进前驱，直接跳到对应分支。只要出现经过指针的写入，就不再假定任何已知的变体。
  - 引用转发扩展到字段等固定位置，并多轮进行；copyprop 移到它前面。
  - 来自调用结果的聚合局部变量从结果缓冲区按字段读出。带指针字段的枚举不这样做，因为非活动变体的数据是无意义的。
  - 结果：`for i in 0..v.len() { v[i] }` 的边界检查消失，求和循环 0.20 → 0.11 s。
  - simplify 只重建确实变动的块。原来每次都复制全部块，并行跑时卡在分配器的锁上，自举慢了约 20%。copyprop 改成写时复制，因为块会被多个函数共享。
- **归纳变量和不等式事实**：
  - prove 在分支边上记录无符号的 `<`/`<=` 关系，判定边界检查时可以经过一个中间值传递；
  - 识别归纳变量 `phi(c0, i + s)`，它在循环里 `>= c0`，所以 `i - k`（`k <= c0`）只要 `i < len` 就也小于 `len`；
  - `for i in 1..v.len() { v[i] - v[i - 1] }` 的两个边界检查都消掉了。
- **寄存器传参**（S7）：
  - 直接调用（目标在编译时确定的实例）把一个或两个字的参数放进寄存器：arm64 用 x1–x7，x64 用 RAX、RCX、RSI、R10、R11；调用方用并行移动放好参数，然后调用 `sym.r`。
  - 每个函数开头有一段栈入口存根，从栈上把这些参数读进寄存器，再落到 `.r`。函数指针、defer、runtime、虚调用、字典调用都走这个入口，不用改。
  - 被调用方在 `.r` 入口用并行移动取出参数，放在帧里的参数存回原位。
  - 栈溢出存根在调用 morestack 前，把参数寄存器存回调用方预留的栈位置，返回后再读回。runtime 搬栈时只修正 x0/x8/x9，不这样做，指向栈的参数指针就会失效（这是多线程下偶发错误的原因，靠二分定位）。
  - 结果：regex 约快 10%，解压约快 12%，自举约快 5%，二进制大约 2%。
  - 结果也走寄存器（2026-11-25，同 Go 的 ABIInternal）：直接调用的结果是一两个字时，被调用方把它放在中转寄存器 V1、V2（arm64 x12、x13，x64 rax、rcx；寄存器分配不用它们，取结果不会有搬动冲突）。调用方把 RET 设成 0（和原来设缓冲区地址一样是一条指令），SSA 里这种调用是 (字, 内存) 的元组，用 Select 取字。被调用方返回时只有 RET 不为 0 才另外写到 RET 指向的缓冲区：经栈入口的调用（函数指针、虚调用、字典调用、defer、runtime）照旧拿内存里的结果，栈入口不用改。没有 defer 的函数在返回时不再检查 defer 链。不超过 16 字节的聚合（结构体、枚举、元组、数组；最后一个字是 1、2、4 或 8 字节）按内存里的字放进 V1、V2，每个字是不是指针照它在内存里的布局，收集器看到的和在内存里一样；`String`、`Vec`、`Option<&T>`、`fmt::Result` 这类结果都不再经过调用方的缓冲区。结果：哈希表计数快约 22%，regex 捕获约 6%，排序约 5%，编译器自举约 5%，二进制小约 1%。
- **大结果直接写进目标变量**（2026-11-25）：结果在内存里（超过 16 字节）、目标是帧里的整个局部变量（不是变量化的、拆开的、装箱的，也不是经 C 函数指针的调用）时，RET 直接指向这个局部变量，省掉结果缓冲区和调用后的拷贝。被调用方只在返回时（defer 之后）把结果拷到 RET，所以参数里引用了这个变量也不会读到半成品。返回结构体的老写法 X25519 59.6 → 49.8 µs，编译器二进制小 1.4%，其他基准不变。
- **带进位的加减**（2026-11-25，同 Go 的 bits.Add64/Sub64）：内建函数 `add_carry`/`sub_borrow`（std 里是 Rust 的 `u64::carrying_add`/`borrowing_sub`，旧编译器调用 `rt::native` 里的同名函数）生成 SSA 的 AddC/SubB，结果是 (和, 进位) 的元组。生成代码前按块做一遍"进位计划"：一个 AddC 的进位输入正好是上一个 AddC 的进位、两者之间没有改标志位的指令时（arm64 上读写内存、搬动和不带检查的整数运算都不改标志位；x64 上只允许 select），进位留在标志位里，直接 adcs/sbcs（x64 adc/sbb）；进位只被这样用的就不再 cset。和、进位直接写进 select 分到的寄存器。四个字的加法因此是 adds、adcs、adcs、adcs 加最后一个 cset。
  - 全量验证中有一次编译器偶发死锁（`all goroutines are asleep`，x64 目标、4 线程模式）。随后用 main 和当前编译器各编译约 1360 次都没有复现；加寄存器传参之前也见过同样的现象，所以更可能是早就存在的低概率 runtime 问题，待查。
